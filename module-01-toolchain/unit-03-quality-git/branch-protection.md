# 分支保护与合并请求

## main 分支的保护规则

| 规则 | 配置 | 为什么 |
| --- | --- | --- |
| 禁止直接 push | 只允许通过合并请求进入 | 所有改动都留一条可追溯的记录 |
| 流水线必须通过 | 要求 `ci` 状态为成功 | 检查没过的代码进不了主干 |
| 至少 1 人评审 | 第 11 周起的项目必需 | 综合项目按小组推进，互相看代码 |
| 分支必须是最新的 | 合并前先 rebase / merge main | 避免合并后才发现冲突 |
| 禁止强推 | 关闭 force push | 主干历史不能被改写 |

## 合并请求里要写什么

```
## 改了什么
一句话说清这次提交干了什么，关联到哪个单元。

## 对应的单元产出
- [ ] unit-05 的数据表格筛选

## 自测
- [ ] 本地 pnpm dev 跑通
- [ ] pnpm lint 无报错
- [ ] 截图或录屏贴在下面（涉及界面改动时）

## 还没做的
明确列出遗留项，别让评审的人猜。
```

## 一个单元一个分支

分支名 `feat/u<单元号>-<简述>`，一个分支只做一件事。做完就合、合完就删，
别攒成一个大分支 —— 大分支评审看不完，冲突也会积重难返。

```bash
git switch -c feat/u05-todo-filter main
# ... 开发 ...
git add -A
git commit -m "feat(u05): 待办清单支持按状态筛选"
git push -u origin feat/u05-todo-filter
```

## 提交前钩子被绕过怎么办

有人用 `git commit -n` 跳过了本地钩子，流水线会在推送后拦下来。
处理方式是补一个修复提交，不要去改主干历史。
